# QNN Conversion Reference

## Scope
Use when `{FLOW}=QNN`.

> **Wrapper scripts vs. direct toolchain calls**
> `qai_convert_fp.py` and `qai_convert_int.py` are the **recommended entry points** for QNN conversion.
> They internally invoke `qnn-onnx-converter` and `qnn-model-lib-generator`, and include **tested auto-detection logic** that resolves known QAIRT toolchain path issues across all supported host architectures (ARM WIN / X86 LINUX / ARM LINUX).
> Preserve-IO policy in wrapper scripts:
> - Default: `--preserve_io` (keep layout + datatype)
> - Fallback: `--preserve_io layout` when target runtime shows FP16/dtype compatibility issues
> Prefer these scripts over calling the toolchain binaries directly.

## Target architecture selection

Omit `--host-arch`,`--target-arch` to let the script auto-detect (picks the most common case for the host OS).

Override explicitly when you need a specific target:

| `--target-arch` | Purpose |
|----------------|---------|
| `x86_64-linux-clang` | Host testing on x86 Linux (auto-detected default on Linux) |
| `aarch64-ubuntu-gcc9.4` | ARM target device support (cross-compile output) |
| `x86_64-windows-msvc` | Host testing on Windows (auto-detected default on Windows) |

> **Note:** `aarch64-ubuntu-gcc9.4` produces a library for ARM deployment; the resulting `.so` cannot be run on an x86 host.


## Preflight

### Cmake Dependencies
**CMake is required** for `qnn-model-lib-generator` to compile model libraries (.dll/.so).

Windows
- Install **Visual Studio** (2019, 2022, or later) with the **"C++ CMake tools for Windows"** component
  - Or install [CMake standalone](https://cmake.org/download/) and add it to PATH
- CMake is typically located at:
  `C:\Program Files\Microsoft Visual Studio\<version>\<edition>\Common7\IDE\CommonExtensions\Microsoft\CMake\CMake\bin\`
  where `<version>` = 2019, 2022, etc. and `<edition>` = Community, Professional, Enterprise
- If `cmake` is not in PATH, add it before running conversion:
  ```powershell
  $env:PATH = "C:\Program Files\Microsoft Visual Studio\2022\Community\Common7\IDE\CommonExtensions\Microsoft\CMake\CMake\bin;" + $env:PATH
  ```

 Linux
```bash
sudo apt install cmake
```

> **Note**: The `qai_convert_fp.py` script checks for CMake before conversion and will fail fast with guidance if it is missing.

### LINUX
#### Temp Directory for Large Models (`QAIRT_TMP_DIR`)

`qnn-onnx-converter` copies external-data ONNX weight files to a temporary directory before
processing. On machines where `/tmp` is a small `tmpfs` (common on Linux servers), this fails
with:

```
ERROR - Encountered Error: Failed to copy external data to the disk at: /tmp/tmpXXXXXX.
It may be due to permission or space issue.
Try setting QAIRT_TMP_DIR environment variable to different location.
```

**Fix**: set `QAIRT_TMP_DIR` to a path with at least **2× the model weight file size** free
before running any converter or wrapper script:

Example (Linux):

```bash
# Check /tmp first
df -h /tmp   # if Use% is 100%, set QAIRT_TMP_DIR

# Point to a directory with enough space
export QAIRT_TMP_DIR=/workspace/qairt_tmp
mkdir -p $QAIRT_TMP_DIR
```

This applies to both direct `qnn-onnx-converter` calls and the `qai_convert_fp.py` /
`qai_convert_int.py` wrapper scripts — they all inherit the env var.

#### Linux cross-compile toolchain note (`aarch64-ubuntu-gcc9.4`)

When building ARM Linux model libraries on a Linux host, `qnn-model-lib-generator` validates the Ubuntu aarch64 toolchain using:

- `QNN_AARCH64_UBUNTU_GCC_94` (sysroot root)
- `${QNN_AARCH64_UBUNTU_GCC_94}/usr/bin/aarch64-linux-gnu-g++` (compiler path)


Required setup:
Install the cross compiler package:

```bash
sudo apt install g++-aarch64-linux-gnu
```

Set the environment variable before conversion/libgen:

```bash
# Typical Ubuntu host setup when compiler is at /usr/bin/aarch64-linux-gnu-g++
export QNN_AARCH64_UBUNTU_GCC_94=/
```

> **Important (not a typo):** `QNN_AARCH64_UBUNTU_GCC_94=/` is the correct value on standard Ubuntu hosts.
> `qnn-model-lib-generator` concatenates `${QNN_AARCH64_UBUNTU_GCC_94}/usr/bin/aarch64-linux-gnu-g++`,
> so setting `/` resolves to `//usr/bin/aarch64-linux-gnu-g++` (equivalent to `/usr/bin/aarch64-linux-gnu-g++`).



Quick verification

```bash
which aarch64-linux-gnu-g++
printf '<%s>\n' "$QNN_AARCH64_UBUNTU_GCC_94"
```

Expected:
- `which` prints `/usr/bin/aarch64-linux-gnu-g++`
- variable is set to `/` (recommended)


##### Recommended persistent setup

Add this to your host QAIRT environment setup script so every conversion run is consistent:

```bash
export QNN_AARCH64_UBUNTU_GCC_94=${QNN_AARCH64_UBUNTU_GCC_94:-/}
```





#### Host Workspace Disk Space

The full conversion pipeline for a single model generates several large intermediate
files on the host. Ensure the workspace has enough free space **before** starting:

| Artifact | Approximate size | Notes |
|---|---|---|
| ONNX file (FP32 inline) | ~4 bytes × param count | e.g. 860M params → ~3.3 GB |
| `.bin` (weight binary) | ~2 bytes × param count (FP16) | generated by converter |
| `.cpp` (graph source) | small (< 5 MB) | generated by converter |
| `.so` / `.dll` (model library) | ~2 bytes × param count (FP16) | generated by libgen |
| Context binary (`.so.bin`) | similar to `.so` | generated by context-binary-generator |

**Rule of thumb**: reserve at least **3× the FP16 model size** in the workspace
(`.bin` + `.so` + `.so.bin` all coexist during generation).

Check free space before conversion:
```bash
df -h .          # workspace free space
df -h /tmp       # temp dir (also needed — set QAIRT_TMP_DIR if low)
```

**Clean up intermediates** after the context binary is generated and validated —
the `.cpp` and `.bin` files are no longer needed for inference:
```bash
rm -f {OUTPUT_DIR}/*.cpp {OUTPUT_DIR}/*.bin
# Keep: .so (needed if regenerating context binary), .so.bin (deployment artifact)
```



### Common failure signatures

- `Could not find compiler: ${QNN_AARCH64_UBUNTU_GCC_94}/usr/bin/aarch64-linux-gnu-g++`
  - Meaning: toolchain variable/path was not resolved as expected by libgen.
  - Fix: ensure `g++-aarch64-linux-gnu` is installed and set `QNN_AARCH64_UBUNTU_GCC_94=/`.
- `fatal error: ... No space left on device`
  - Meaning: compilation ran but failed due to host disk/tmp capacity.
  - `qnn-model-lib-generator` uses `objcopy` to embed the `.bin` weight file into the
    `.so`. This requires approximately **2× the `.bin` file size** of free space in the
    build directory (default: a temp dir under the workspace). For a 1 GB `.bin`, you
    need ~2 GB free.
  - Fix: free workspace space (remove stale `.cpp`/`.bin` files from prior runs), or
    point the build to a larger volume by setting `QAIRT_TMP_DIR`.


## Conversion
`qnn-onnx-converter` converts ONNX models to QNN graph artifacts. The AIPC wrapper
scripts are the preferred entry points:

- `scripts/qai_convert_fp.py` for FP32 or FP16 conversion.
- `scripts/qai_convert_int.py` for quantized conversion, including INT16, INT8, and INT4
  activation, weight, and bias settings.

Prefer the wrapper scripts for normal conversion. Use direct `qnn-onnx-converter` and
`qnn-model-lib-generator` calls for low-level diagnostics, toolchain debugging, or
advanced cases the wrappers do not expose.

Key conversion decisions:

| Decision | Guidance |
|----------|----------|
| Dry run | Use `qnn-onnx-converter --dry_run` to check converter support before doing a full conversion. |
| Precision | Use the FP wrapper for FP32 or FP16 output; use the INT wrapper for quantized output. |
| Quantization | Prefer wrapper bitwidth flags for common cases. Use AIMET encodings only when the model already has an AIMET quantization flow or explicit encodings are required. |
| Simplification | Direct converter option: use `qnn-onnx-converter --no_simplification` to skip automatic ONNX simplification when simplification changes model behavior or causes converter issues. This is often useful on Windows on Snapdragon / QAIRT 2.45-era flows. `qai_convert_fp.py` does not currently expose a wrapper `--no-simplification` flag. |
| IO preservation | Start with `--preserve-io-mode datatype` to preserve layout and datatype. If the target runtime has FP16 or datatype compatibility issues, retry with `--preserve-io-mode layout`. |
| Static shapes | NPU deployment requires static input shapes. For dynamic ONNX inputs, pass explicit dimensions with `--input-dim`. |

> **Agent note:** Before conversion, inspect the ONNX inputs. If any input dimension is
> symbolic, unknown, or `0`, add one `--input-dim` entry for each dynamic input.

### Direct QNN toolchain flow

The wrapper scripts run the same two-stage QNN toolchain flow shown below. Use this
section to understand the generated artifacts, debug wrapper behavior, or run a direct
converter/libgen command when wrapper behavior is not enough.

1. `qnn-onnx-converter` converts `model.onnx` to:
   - `model.cpp`: generated QNN graph source.
   - `model.bin`: generated binary weights.
   - `model_net.json`: generated network metadata.
2. `qnn-model-lib-generator` compiles `model.cpp` and `model.bin` into:
   - `.so` on Linux.
   - `.dll` on Windows.

#### Step 1: ONNX to C++/BIN

General form:

```bash
${QAIRT_SDK_ROOT}/bin/<host-toolchain>/qnn-onnx-converter \
  --input_network /path/to/model.onnx \
  --output_path /path/to/output/model.cpp \
  --float_bitwidth 16 \
  --preserve_io
```

Windows PowerShell form:

```powershell
python "$env:QAIRT_SDK_ROOT\bin\x86_64-windows-msvc\qnn-onnx-converter" `
  --input_network C:\path\to\model.onnx `
  --no_simplification `
  --output_path C:\path\to\output\model.cpp `
  --float_bitwidth 16 `
  --preserve_io
```

Expected converter output:

```text
INFO - Model CPP saved at: output/model.cpp
INFO - Model BIN saved at: output/model.bin
INFO - Conversion complete!
```

Notes:

- Use `--float_bitwidth 16`, not deprecated `--float_bw 16`.
- `--output_path` sets the graph stem used by the model library generator.
- `--no_simplification` is often useful on Windows on Snapdragon; use it when simplification changes model behavior or causes converter issues.
- ONNX opset 18 is supported by recent QAIRT versions.
- For large external-data ONNX models, pass the `.onnx` path. The converter discovers the matching `.onnx.data` file automatically when it is beside the model.
- For dynamic inputs, direct converter syntax is `--input_dim input_name dim1,dim2,...`. The wrapper syntax is `--input-dim input_name,dim1,dim2,...`.

#### `--preserve_io` modes

`qnn-onnx-converter` accepts one preserve-IO form per invocation:

| Direct converter form | Meaning |
|-----------------------|---------|
| `--preserve_io` | Preserve both layout and datatype for all input/output tensors. |
| `--preserve_io layout [names...]` | Preserve layout only, for the listed tensors or all tensors when names are omitted. |
| `--preserve_io datatype [names...]` | Preserve datatype only, for the listed tensors or all tensors when names are omitted. |

Wrapper mapping:

| Wrapper option | Direct converter option emitted |
|----------------|---------------------------------|
| `--preserve-io-mode datatype` | `--preserve_io` |
| `--preserve-io-mode layout` | `--preserve_io layout` |
| `--preserve-io-mode none` | no preserve-IO option |

> **Important:** The wrapper name `datatype` is historical in this repository. It maps
> to bare `--preserve_io`, which preserves both layout and datatype. It is not the same
> as direct converter form `--preserve_io datatype`. The wrappers do not currently
> expose per-tensor name lists or direct datatype-only preservation.

> ⚠️ **Windows path and x86 path only .** `--preserve-io-mode` is applied on the `qnn-onnx-converter`
> (Windows) branch. On ARM Linux both wrappers take the `qairt-converter` → `.dlc` branch, which
> ignores the flag: `qai_convert_int.py` always emits bare `--preserve_io`, and
> `qai_convert_fp.py` emits none. Call `qairt-converter` directly if you need a specific
> sub-mode on Linux.

If the target HTP does not support a preserved datatype, for example FP16 on some SoCs,
retry with layout-only preservation.

#### Step 2: C++/BIN to model library

General form:

```bash
${QAIRT_SDK_ROOT}/bin/<libgen-toolchain>/qnn-model-lib-generator \
  --cpp /path/to/output/model.cpp \
  --bin /path/to/output/model.bin \
  --lib_targets <target-lib-arch> \
  --lib_name model \
  --output_dir /path/to/output
```

Windows form:

```powershell
python "$env:QAIRT_SDK_ROOT\bin\<libgen-toolchain>\qnn-model-lib-generator" `
  -c C:\path\to\output\model.cpp `
  -b C:\path\to\output\model.bin `
  -o C:\path\to\output `
  -t <target-lib-arch>
```

Expected libgen output:

```text
INFO - Library name         : model
INFO - Generated model library path: output/<arch>/model.<so-or-dll>
```

The toolchain folder and target library architecture must match the platform where the
model library will be loaded. Examples:

| Platform/use case | Converter host toolchain | Libgen toolchain | Target library arch |
|-------------------|--------------------------|------------------|---------------------|
| Linux x86 host testing | `x86_64-linux-clang` | `x86_64-linux-clang` | `x86_64-linux-clang` |
| Linux ARM deployment from Linux host | `x86_64-linux-clang` | `x86_64-linux-clang` | `aarch64-ubuntu-gcc9.4` |
| Windows x86_64 process | `x86_64-windows-msvc` | `x86_64-windows-msvc` | `windows-x86_64` |
| Windows ARM64 native DLL | `x86_64-windows-msvc` | `aarch64-windows-msvc` | `windows-aarch64` |

On Windows on Snapdragon, choose the target library architecture for the process that will
load the model library. Use `windows-x86_64` for x86_64-emulated Python or tooling. Build
`windows-aarch64` only for native ARM64 loading, and ensure the ARM64 Visual Studio
toolchain environment, such as `vcvarsall.bat arm64`, is active.

### Explicit input dimensions for dynamic inputs

If the ONNX model has dynamic input shapes, you must specify explicit dimensions using `--input-dim`:

```bash
python scripts/qai_convert_fp.py \
  --onnx model.onnx \
  --precision 16 \
  --output-root qnn_output \
  --input-dim input,1,3,64,64
```

Format:

```text
--input-dim input_name,dim1,dim2,dim3,...
```

Use the ONNX input name exactly. The dimension order must match the model's declared input
layout, for example NCHW `1,3,224,224` or NHWC `1,224,224,3`.

Specify multiple dynamic inputs by repeating the flag:

```bash
python scripts/qai_convert_fp.py \
  --onnx model.onnx \
  --precision 16 \
  --input-dim input1,1,3,224,224 \
  --input-dim input2,1,10
```

### Float conversion (FP16/FP32) example

```bash
python scripts/qai_convert_fp.py \
  --onnx model.onnx \
  --precision 16 \
  --output-root qnn_output \
  --preserve-io-mode datatype
```

Use `--precision 32` for FP32 output. Use `--precision 16` for FP16 output.

If the target runtime shows FP16 or datatype compatibility issues, retry with layout-only
IO preservation:

```bash
python scripts/qai_convert_fp.py \
  --onnx model.onnx \
  --precision 16 \
  --output-root qnn_output \
  --preserve-io-mode layout
```

Expected output artifacts:

- `model.bin`
- `model.cpp`
- `model_net.json`
- compiled model library (`.so` or `.dll`)

### Quantized conversion (INT8/INT16/INT4) example

```bash
python scripts/qai_convert_int.py \
  --input_network model.onnx \
  --input_list calibration_list.txt \
  --output-root qnn_output \
  --act_bw 8 \
  --weight_bw 8 \
  --preserve-io-mode datatype
```

Common quantization presets:

| Preset | Flags | Notes |
|--------|-------|-------|
| A16W8 | `--act_bw 16 --weight_bw 8` | Default and commonly recommended for vision models. |
| A8W8 | `--act_bw 8 --weight_bw 8` | Standard INT8 activation and weight quantization. |
| A8W8B8 | `--act_bw 8 --weight_bw 8 --bias_bw 8` | INT8 activation, weight, and bias quantization. |
| A16W4 | `--act_bw 16 --weight_bw 4` | Lower weight bandwidth while keeping wider activations. |
| A8W4 | `--act_bw 8 --weight_bw 4` | Most compact listed preset; validate accuracy carefully. |

If the target runtime shows FP16 or datatype compatibility issues, retry with layout-only
IO preservation:

```bash
python scripts/qai_convert_int.py \
  --input_network model.onnx \
  --input_list calibration_list.txt \
  --output-root qnn_output \
  --act_bw 8 \
  --weight_bw 8 \
  --preserve-io-mode layout
```

> **Troubleshooting**: If conversion fails with "Unsupported operator" errors, see [In-Memory Operator Patching](operator_patching.md) for patching guidance.

### Converter dry-run

Dry run is a quick converter support check. It does not generate final QNN artifacts.

Verify that the converter binary exists for the host architecture before running it:

```bash
# Linux x86 host
ls ${QAIRT_SDK_ROOT}/bin/x86_64-linux-clang/qnn-onnx-converter

# Linux ARM host
ls ${QAIRT_SDK_ROOT}/bin/aarch64-linux-gcc/qnn-onnx-converter
```

```powershell
# Windows ARM host using x86_64 QAIRT tools under emulation
Test-Path "$env:QAIRT_SDK_ROOT\bin\x86_64-windows-msvc\qnn-onnx-converter"
```

Run dry-run with the matching toolchain binary:

```bash
# Linux x86 host
${QAIRT_SDK_ROOT}/bin/x86_64-linux-clang/qnn-onnx-converter \
  --input_network model.onnx \
  --dry_run

# Linux ARM host
${QAIRT_SDK_ROOT}/bin/aarch64-linux-gcc/qnn-onnx-converter \
  --input_network model.onnx \
  --dry_run
```

```powershell
# Windows ARM host using x86_64 QAIRT tools under emulation
python "$env:QAIRT_SDK_ROOT\bin\x86_64-windows-msvc\qnn-onnx-converter" `
  --input_network model.onnx `
  --dry_run
```
